# Threat model

A live executor can move the funds in the hot wallet. Default boot leaves `WHALE_BROADCAST` unset and does not broadcast. If `LISTING_TRADER_LIVE` is set, boot throws. If `WITHDRAW_ENABLED` is set, boot throws. `POST /withdraw` is absent. This page uses STRIDE so each control is tied to a threat. The controls are what the code does. They are not a promise about an exchange or a signer vendor.

## Spoofing

`EXECUTOR_AUTH_TOKEN` is required at boot and must be at least 16 characters. `RESOLVER_AUTH_TOKEN` is required only when `RESOLVER_URL` is set, and the two tokens must differ. `STRATEGY_CAPS_JSON` throws at boot, so there is no strategy bearer. Mutating routes compare `Authorization: Bearer` with SHA-256 and `timingSafeEqual`. `GET /health` is the only open route and returns only `{"ok":true}`. The public config is on an authenticated `GET /status`. Secrets, the router list, and the approval cache are not in either payload.

The executor token guards `POST /execute` and `POST /rebalance`. A bearer that does not match gets 401. This tree has no resolver process. A missing, short, or reused token refuses boot.

## Tampering

Zod parses every request and every aggregator or screening body this service acts on. A mismatch is a 400 or a null quote. Firm quotes are checked again against the slippage cap before sign.

App policy constrains the chain, native value, router, Solana instructions, and, where the calldata can be decoded, the swap recipient. Per provider:

- Solana (Jupiter): the destination token account must belong to the hot wallet, checked per instruction below.
- KyberSwap (MetaAggregationRouterV2 `swap` and `swapSimpleMode`): the signer decodes `desc.dstReceiver` and refuses any recipient but the hot wallet. Before signing, the sender requires `desc.dstToken` to be the bought token, `desc.srcToken` and `desc.amount` to equal the leg's sold token and amount, and `desc.minReturnAmount` to clear ours. Every provider's native `transaction.value` must equal the leg's native input, or zero for a token input.
- 0x (`AllowanceHolder.exec` wrapping `Settler.execute`): the signer decodes `slippage.recipient` and refuses any recipient but the hot wallet. The sender requires `slippage.buyToken` to be the bought token and uses `slippage.minAmountOut` as the minimum. Settler checks that minimum against what it pays the recipient. `exec` lends the sell-token allowance to `operator` for one call into `target`, so the signer requires `operator` to equal `target` and both to be in `ZEROX_SETTLER_ALLOWLIST_JSON` for that chain. The sender requires the `exec` token and amount to be the leg's sell token and amount. Direct `Settler.execute` is refused while its `actions` and sold input are not decoded. An AllowanceHolder `exec` whose inner call is not Settler `execute` is refused. Settler addresses rotate, and the 0x-settler README says not to hardcode them, so the list is operator config: when 0x deploys a new Settler, 0x swaps are refused until the list names it.
- LI.FI: the calldata targets the LI.FI diamond with facet-specific encodings this app does not decode, so the recipient is not checked. LI.FI is quote-only. `LIFI_LIVE=true` throws at boot until facet, recipient, token, input, and minimum-output validation exists.

Calldata to an allowlisted router that decodes as none of these is refused. The Turnkey EVM policy constrains only the router in `eth.tx.to`, the chain, the native value cap, the selector prefix, and the chain's `eth.tx.gas` and `eth.tx.max_fee_per_gas` limits from `DEFAULT_EVM_FEE_LIMITS` or `EVM_FEE_LIMITS_JSON`. A chain without a fee limit matches no clause. Optimism, Base, Blast, and Scroll render no clause even with a limit, because Turnkey cannot see their L1 data fee. The app and whale-signer bound that fee with a fixed per-transaction budget and a calldata cap. Enclave wallets stay closed on these chains until the owner accepts relying on Whale's code for that bound. Turnkey cannot multiply fields, so the two limits are separate bounds whose product is the worst-case fee. A wallet keeps the limits it was delegated with until its owner re-runs delegation. The Turnkey policy cannot see the swap recipient, so that check lives in the app policy and the pre-sign simulation. The Turnkey Solana policy constrains native transfer recipients and program ids. Each Turnkey policy is scoped to one wallet with `wallet.id`. The checked-in file is `policies/turnkey.json`, a template with placeholder ids. `ROUTER_ALLOWLIST_JSON` is a map of chain id to router addresses. A router allowed on one chain is denied on another. An empty list for that chain denies the swap. `DEFAULT_ROUTERS` in `src/chains.ts` fills a chain that the executor's or the gateway's `ROUTER_ALLOWLIST_JSON` does not name. It holds only Monad (143): the 0x AllowanceHolder `0x0000000000001fF3684f28c67538d4D072C22734` and the KyberSwap MetaAggregationRouterV2 `0x6131B5fae19EA4f9D964eAc0408E4408b66337b5`. Naming 143 in the map replaces both, and `"143": []` denies Monad swaps. A deployment manifest gets no defaults. Its `routers` map is the whole allowlist, so a manifest allows Monad only when it names 143. A token sell with a non-zero native value is denied. Solana program ids outside the base set plus `SOLANA_PROGRAM_ALLOWLIST` deny the signature. `SOLANA_PROGRAM_ALLOWLIST` adds program ids. It does not replace the base set.

The app decodes every top-level instruction of a base program against a default-deny table in `signing-policy.ts`. An instruction that is not in the table is denied. The table allows these:

- System Program Transfer from the hot wallet to the hot wallet, an allowlisted withdraw address, the hot wallet's wrapped SOL account, or a published Jito tip account. Tips across the transaction may total at most `JITO_TIP_LAMPORTS`. Assign, CreateAccount, TransferWithSeed, AdvanceNonceAccount, and every other System instruction are denied.
- Token and Token-2022 SyncNative, CloseAccount that pays the hot wallet, InitializeAccount3 owned by the hot wallet, and Transfer or TransferChecked into an associated token account of the hot wallet or an allowlisted withdraw address. Approve, ApproveChecked, SetAuthority, and the rest are denied.
- Associated Token Account CreateIdempotent funded by the hot wallet for the hot wallet or an allowlisted withdraw address.
- Compute Budget unit limit, unit price, and loaded-data limit. Unit price times unit limit (1.4M units when no limit is set), plus Jito tips, may total at most `SOLANA_MAX_PRIORITY_LAMPORTS`.
- Jupiter `sharedAccountsRoute` only (#120). In that instruction Jupiter moves `inAmount` out of the source account itself, so the sold token is the one the spend cap charges. The signing table requires the transfer authority, source, destination, and platform fee slots to be static keys. The authority must be the hot wallet, and the hot wallet may appear in no other account slot, so no route step gets its signature. The platform fee slot must be the Jupiter program, and the destination must be the hot wallet's wrapped SOL account or its Token-program account for the bought mint. When the bought-mint slot comes from a lookup table, the signing table accepts only SOL, USDC, or USDT as that mint. The broadcast path also derives the source from the sold mint and the destination from the bought mint, and requires instruction input, quoted output, slippage, and minimum to match the authorized quote. `route` is denied because each of its steps sells from accounts it names, under the hot wallet's signature (#62). Quotes are always `exactIn`, so the exact-out routes are denied, as are the token-ledger and newer v2 routes. A buy into a Token-2022 account is denied for now.

An account that comes from an address lookup table cannot be checked offline, so a rule that needs it denies the signature. Instructions of an extra program from `SOLANA_PROGRAM_ALLOWLIST` are not decoded. Only add a program you trust with the hot wallet's signature.

The Turnkey Solana policy allows native transfers only to the hot wallet, its wrapped SOL account, or a Jito tip account, and denies every top-level SPL transfer. Turnkey's policy language has no condition that derives an owner's associated token account for an arbitrary mint, so SPL recovery under Turnkey needs a root-quorum approval. The Turnkey EVM policy checks chain, router, native value, and, when `selectors` is passed, the first four bytes of calldata through `eth.tx.data[0..10]`. `eth.tx.function_name` needs an ABI uploaded to Turnkey for each router, so the policy does not use it. The app does not check router selectors.

Pre-sign simulation is viem `simulateCalls` on EVM and `simulateTransaction` on Solana. A revert is `simulation rejected the transaction` and `broadcast` is false, so the spend reservation is released.

In live mode the `MIN_LIQUIDITY_USD` check ignores the `pairMap` the caller sends. The executor reads the token's pools from DexScreener (`DEXSCREENER_API_BASE`) and counts only pools on the same chain that pair the token with a quote asset from `QUOTE_ASSET_ALLOWLIST_JSON` or the defaults. The deepest such pool is the figure. A failed or timed-out lookup is `liquidity unknown`. That token is not traded, the intent can still use a liquid alternate, and it never falls back to Hyperliquid. The figure is read fresh for each trade, not cached. A token on a disabled chain is not looked up. A chain with no DexScreener slug (`robinhood`, `hyperevm`, `monad` by default) or no default quote asset (`bnb`) refuses live swaps until `DEXSCREENER_CHAIN_SLUGS` or `QUOTE_ASSET_ALLOWLIST_JSON` covers it. Dry-run still uses the caller's `pairMap`, so a quote works for a token with no pair data.

`TOKEN_SCREENING=true` rejects a live-lookup token when GoPlus or Blockaid fails, times out, or reports a honeypot, `cannot_sell_all`, or a result other than `Benign`. That path is the unlisted fallback only.

## Repudiation

pino logs the execution report. Authorization, API keys, and OKX signature headers are redacted. `redactError` still strips a 64-hex key and a long base58 string. The spend journal records the idempotency key, the strategy id (`listing` for alerts), the USD amount, the UTC day, and `reserved`, `committed`, or `released`. `signed_tx` records every signed hash with its nonce.

## Information disclosure

With Turnkey, the trading keys are not in this process. The process holds the Turnkey API key, which can request a signature inside the policy. The local keystore decrypts into the process only for a dry-run. Live mode does not accept it. Live boot refuses to start when `EVM_PRIVATE_KEY`, `SOLANA_SECRET_KEY`, `HYPERLIQUID_AGENT_KEY`, `KEYSTORE_PATH`, or `KEYSTORE_PASSPHRASE` is set. A dry-run deletes those variables from `process.env` after it loads them. Every config API key, the auth and admin tokens, the notifier URL, and the Turnkey key are redacted from error text. A Hyperliquid signature from Turnkey must recover to the agent address before it is submitted. Logs do not print `Secret` values.

Do not attach a Railway public domain. Boot throws when `RAILWAY_PUBLIC_DOMAIN` is set. Use the private network URL for Postgres. Leave `RESOLVER_URL` unset. This tree has no resolver process.

## Denial of service

Fastify limits the body to 32 KiB. The global rate limit is 60 a minute. `POST /execute` and `POST /rebalance` are 10 a minute. Provider calls have a per-minute budget, a 350 ms timeout, and a 500 ms deadline. Three failures, or one compliance response, open that provider. A compliance skip is not retried on another host.

## Elevation of privilege

`POST /withdraw` is absent. Setting `WITHDRAW_ENABLED` throws at boot. The signing policy still refuses a `withdraw` purpose whose destination is not on `OWNER_WITHDRAW_ADDRESSES`. An empty allowlist makes `POST /rebalance` skip with `bridge allowlist is empty`. Bridge plans set `broadcast` to false.

The HyperCore agent path signs only `order`, `cancel`, and `updateLeverage`. It refuses `withdraw3`, `usdSend`, `spotSend`, `sendAsset`, `agentSendAsset`, `usdClassTransfer`, `vaultTransfer`, and `approveAgent`. Turnkey's Agent policy cannot see those names inside `connectionId`. The ban is in this process, before submit. Load the agent key, not the master key. The signing policy also requires each action to have exactly the fields Whale builds. An order must be immediate-or-cancel, must not be on a builder-deployed perp (asset 100000 and up), and its notional at the limit price must stay within `MAX_USD_PER_TRADE` plus the hard slippage maximum. A perp sell with no long opens a short. A sell's limit price is only a floor, so a notional check at that price bounds nothing. A sell of any size at a near-zero price fits the per-trade USD cap. The signing policy therefore charges every sell by its size, summed per key across the action. A perp sell (asset below 10000), reduce-only or opening, charges `hypercore:perp:<asset>:sold`. A spot sell (asset 10000 to 99999) charges `hypercore:spot:<asset>:sold`. Both keys are in `HYPERCORE_SELL_LIMITS`, in 1e-8 units of the sold asset, and a sell is refused when no limit is set for its key. Boot rejects a key that no sell would charge, such as a leading-zero asset or a perp key with a spot index. whale-signer bounds each sell by its size per day, and the app's policy bounds each signature by the same limit. Neither bounds a short by USD. A Hyperliquid order carries no margin mode, and Hyperliquid uses cross margin by default, so under cross margin a short can lose up to the whole HyperCore perp balance. Neither signer can force isolated margin on an order. Jhonny accepted this on 2026-11-19 to keep shorts. The executor's daily reservation still counts the intent's notional. The L1 hash and both signatures match the Hyperliquid Python SDK test vectors, including its production connection id (`test/hypercore-signing.test.ts`).

Perp leverage is isolated only. Leverage is account state that Hyperliquid keeps per asset, not a property of one order. Hyperliquid's default for an asset is cross margin, and it rejects a change of margin mode while a position is open. Before each perp trade, Whale reads `clearinghouseState` for `HYPERLIQUID_ACCOUNT_ADDRESS` and plans the leverage step from the position the account holds in that coin. With no position, Whale sends an isolated `updateLeverage` first, at the intent's `leverage` or 1 for a buy, and at 1 for a sell, so neither a long nor a short opens at the cross default. With a position open, Whale sends no `updateLeverage`, so a leverage change cannot stop a close. The one exception is a buy that sets `leverage` on an open isolated long, which sends that leverage. A buy that sets `leverage` on an open cross long is refused. A buy on a short and a sell on a long run at the position's own setting. When the position cannot be read, or no account address is set, the trade is skipped with `hyperliquid position unreadable`, and a close is skipped too. The position read waits up to 5 seconds. On 2026-11-25, `clearinghouseState` for a mainnet account with 177 positions (a 65 KB answer) took 0.5 to 1.2 seconds over 40 cold reads, and the old 1.5 second bound timed out on it. A Hyperliquid `/info` outage or a link slower than that bound still blocks a close. On the local MCP, when `HYPERLIQUID_ACCOUNT_ADDRESS` is not whale-signer's own EVM address, each perp trade, a dry run included, first checks `extraAgents` for that account and fails with `hyperliquid agent is not approved` unless the key is an approved agent that has not expired. Without that check, Whale would plan the leverage step from that account's position while Hyperliquid places the order on the key's own account. An intent that sets `leverage` on a sell is refused. Leverage above 1 is refused on any venue but a HyperCore perp. The app's signing policy refuses an `updateLeverage` above `MAX_PERP_LEVERAGE`, and whale-signer refuses one above `hypercore.maxLeverage` in its policy file. Both default to 3, the ceiling Jhonny set on 2026-11-20. Both refuse a ceiling above 50 at boot. The highest `maxLeverage` in Hyperliquid's `meta` on 2026-11-20 was 40. Boot refuses the old `MAX_LEVERAGE` name, so a stale value cannot be dropped in silence. The executor also refuses leverage above the asset's own `maxLeverage` in Hyperliquid's `meta`. Neither signer reads `meta`, and Hyperliquid enforces that maximum again at the exchange.

Leverage does not raise any USD cap. The per-trade cap, both signing policies, and the daily reservation count an order's notional, its price times its size. A 5 USD order at 3x is 5 USD of exposure on about 1.67 USD of margin. Leverage raises the liquidation risk. Hyperliquid sets the maintenance margin at half the initial margin at the asset's maximum leverage. An isolated long at 3x is liquidated after a fall of about 32% on ETH (maximum 25x) and about 20% on GMX (maximum 3x). Liquidation takes the position's whole isolated margin, and the liquidation fee comes out of it. Neither signer sees the account's current leverage or margin mode. An order without the `updateLeverage` step, sent by Whale on an open position or by a compromised Whale, runs at the leverage and margin mode the account already has for the asset. A buy larger than an open short, or a sell larger than an open long, flips the position, and the new side keeps the old position's setting. The notional caps still bound each order.

A HyperCore withdrawal (`withdraw3`) is a user-signed action, so an agent key cannot sign it. Only the wallet's own EVM key signs it, through `signHyperliquidWithdraw`, and the Turnkey backend does not offer that method. The signing policy pays only the wallet's own address or `OWNER_WITHDRAW_ADDRESSES`. It also requires the configured network's `hyperliquidChain` and `signatureChainId` 0x66eee, and an amount at most `MAX_WITHDRAW_AMOUNT`. `withdrawHypercore` reserves the amount in the withdraw journal under `hypercore:usdc` against `MAX_WITHDRAW_DAILY_AMOUNT` before it signs. It releases the reservation when the signer refuses or Hyperliquid rejects the withdrawal. It keeps the reservation when the answer is lost. Hyperliquid pays the withdrawal on Arbitrum to the same address. No route calls it yet, and `WITHDRAW_ENABLED` stays closed.

`KILL_SWITCH=true`, or the `kill_switch` row in `control_flags`, skips new buys on `POST /execute`. Neither deletes a key. Revoke the Turnkey API user to stop signing. See the [runbook](runbook.md).

The daily cap is enforced inside a Postgres transaction with one advisory lock per day. A second executor cannot pass the boot advisory lock when `DATABASE_URL` is set, and `railway.json` runs one replica, so the in-memory idempotency map is never shared.

A compromised or mispriced Hyperliquid agent could try to drain the account through IOC orders crossed far from the mark. The app bounds that path before signing: the order size comes from the per-trade USD cap, and the limit price is the mark moved by at most the slippage cap, rounded to the venue wire format. An order the venue reports as an error, or that fills nothing, releases the spend reservation. The market comes from the token's address, not from the caller or the token symbol. A HyperCore token (`chainKey` `hypercore`) names its perp by its address, which is looked up in Hyperliquid's own `meta`. A HyperEVM token maps to the spot pair against USDC whose token has that `evmContract` in `spotMeta`. The asset index, size decimals, and mark price key come from that entry. A token on any other chain, a delisted perp, or a contract Hyperliquid does not link has no Hyperliquid route, so a thin token on another chain no longer falls back to HyperCore. When the caller's `hyperliquid.coin` or `hyperliquid.assetIndex` differs from the resolved market, the intent is refused. A caller cannot name one token and trade another market. A valid claim names the Hyperliquid coin (`HYPE`, or the spot base token such as `UBTC`) and the full asset index (`159` for a perp, `10000` plus the pair index for spot, such as `10142`). A HyperCore token on a disabled `hypercore` chain uses its liquid alternates, as before.

## What this does not cover

A quoted router can still be a hostile contract the aggregator returned, inside the allowlist you configured. The caps bound the size. Screening does not run on the watchlist hot path. Research CI does not run these tests and does not fetch market data for them.
