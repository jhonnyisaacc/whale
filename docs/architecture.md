# How a listing becomes a sized route

The collector is outside this tree. It hears a listing and `POST`s an alert to the executor `/listing` route. The executor asks the resolver, then either logs a dry-run buy or, when live mode is on, signs a transaction. Rocket never sees that path. `rocket/` does not import `wallet/`.

## The watchlist is the hot path

Each token record holds a ticker, every project name the resolver has (English, and Korean when CoinGecko returned one), the chain, the contract, and a pair map. The pair map is every pool for that contract on that chain, sorted by liquidity. Only pools whose quote address is on the chain's quote-asset allowlist are kept (USDC, USDT, the wrapped native token, and wSOL on Solana, from `chains.ts` or `QUOTE_ASSET_ALLOWLIST_JSON`). A pool pairing the token with a counterfeit "USDC" is dropped before liquidity is ranked. `top` is the deepest kept pool. For MPLX that is often MPLX against SOL, with a thinner MPLX against USDC kept beside it.

The resolver keeps that list in memory, keyed by exact ticker. A hit needs the ticker and a full project-name match after Unicode normalization. `AXIS` does not match `AXS`. A ticker with the wrong name is a lookalike and stops. When the same name is liquid on more than one chain, the hit is the cheaper chain (`feeRank` in `src/chains.ts`) and the others come back as `alternates`. Two tradable contracts on the same chain stay ambiguous. A token under the liquidity floor is illiquid unless it has a Hyperliquid perp. The executor uses that perp only when the primary pool is thin and no liquid alternate exists.

Postgres is the shared copy. The memory map is per process. On boot the resolver loads `verified_tokens` when `DATABASE_URL` is set. `REFRESH_ENABLED=true` rebuilds identities about once a day from the CoinGecko coin list and refreshes pools for the shortlist on `LIQUIDITY_REFRESH_MS` (default 10 minutes, inside the 5 to 15 minute band). The shortlist is the tokens that already have pools, capped by `SHORTLIST_LIMIT` (default 200), deepest first. A full rebuild keeps those pools. It does not ask DexScreener for the whole coin list.

An unlisted alert gets one DexScreener search, bounded by `LIVE_LOOKUP_TIMEOUT_MS` (default 400). The search has to match ticker and project name on one contract. A timeout, a miss, or two contracts returns no buy. A dry-run match that clears the pool floor and the coin list is returned and not stored. Live mode reports the lookup and does not buy it. When screening is on, a honeypot, a buy or sell tax above `MAX_TOKEN_TAX`, or a failed vendor response rejects the contract. Live mode turns screening on unless `TOKEN_SCREENING=false`. A refresh drops a pooled token that fails the same check, and a live buy checks again before it sends.

CoinGecko platform ids are mapped only where the key is the usual public id (`ethereum`, `base`, `solana`, and the other keys in `PLATFORM_TO_CHAIN`). Robinhood Chain and HyperEVM are not in that map. DexScreener slugs for those two chains were not confirmed, so pool refresh ignores them until `DEXSCREENER_CHAIN_SLUGS` sets a slug.

## The executor spends what the wallet holds

`WALLET_HOLDINGS_JSON` lists symbol, address, a USD hint, whether the balance is the native gas token, decimals, and `chainKey` when the address belongs to one chain. Dry-run uses the JSON amount. Live mode replaces that amount with the balance read for the candidate chain and the USD value with that amount at the CoinGecko price, refreshed every 30 seconds. A price older than `PRICE_MAX_AGE_MS` skips the holding, and the buy skips with `holding price stale` when no holding is priced. A holding with no `chainKey` is eligible on every chain where its address is valid. Native gas follows its asset. SOL is eligible only on Solana. ETH is eligible only on an EVM chain whose native asset is ETH. BNB, POL, MON, and HYPE are eligible only on their own chain. An untagged native row that does not name one of those assets is rejected when the JSON loads. Live mode reads and sizes an eligible holding on each of those chains. An address from another chain is skipped. A null or thrown read skips that holding and leaves the other holdings. The candidate is skipped when none of its holdings are read, and the other candidates still quote. The buy is skipped when every candidate is skipped. A named `chainKey` is read on that chain and spent only there. An unknown `chainKey` is rejected when the process loads the JSON. The planner drops a native balance that would cross the chain's reserve, about 2 USD of gas in native units (0.02 SOL, 0.001 ETH on L2s, 0.002 ETH on Ethereum, 0.004 BNB, 25 POL, 0.03 HYPE, 100 MON). It sizes the sell to the trade notional, default 5 USD, and converts it with the holding's decimals. Missing decimals skip the route with `holding decimals missing` rather than a guessed unit size.

For each spendable holding the planner builds two candidates.

- An aggregator hop from that holding to the token. Jupiter on Solana, and 0x on the chains it lists, can fill USDC to SOL to the token inside one quote.
- An explicit two-hop when the deepest pool's quote is a different asset. The first leg buys that quote. The second leg sells the amount the first quote returned.

Quotes that do not return a price impact are dropped. 0x has no impact field, so impact is the gap between USD spent and the bought amount at the pool price. That needs the buy token's decimals and USD price. Watchlist build reads ERC-20 `decimals()` from the chain RPC and caches the result. A quote reads it once more when the cache is empty. The hop is skipped when the decimals stay unknown. A bad aggregator body is dropped. The other providers in that race still compete. Jupiter's `priceImpactPct` example is `0.0001` with no stated unit. The default treats it as a fraction (`0.0001` becomes 0.01 percent). Set `JUPITER_IMPACT_UNIT=percent` if a response is already in percent. The default quote path stays Swap V1 (`JUPITER_API_BASE`, default `https://api.jup.ag/swap/v1`) because this service signs the unsigned transaction and can hand it to Jito. Jupiter's Swap V2 `/order` and `/execute` path lands the transaction at Jupiter, so it is not the default. `JUPITER_API_BASE` overrides the origin.

Each enabled chain asks every aggregator that lists it, in parallel, and ranks what returned by the earlier of `QUOTE_DEADLINE_MS` and `RACE_GRACE_MS` after the first signable quote. It also stops once every signable provider has answered and one of them gave a usable quote. Candidate chains and route plans are quoted at the same time, and screening runs alongside them. Only the send waits for the verdict. 0x is asked only with `ZEROX_API_KEY`. LI.FI is asked with the wallet as `fromAddress`. Signable quotes are Jupiter, 0x allowance-holder, and KyberSwap build, plus LI.FI same-chain when `LIFI_LIVE=true`. 1inch, Velora, and OKX are quote-only until their firm-swap bodies are pinned. If an unsigned quote has a better net, the report note names it and the service still signs the best signable route. Odos is not called. Jumper is the LI.FI interface, not a second client. See [fees](fees.md).

Two-hop impact compounds. One percent then one percent is 1.99 percent. The picker drops `signable: false`, keeps routes inside the slippage cap (default 100 bps, hard max 300), and sorts by net output after the fee and a gas ceiling, then impact, then fee USD, then `feeRank`, then buy amount. A quote that omits gas pays the ceiling, so it cannot look free. An explicit two-hop goes through the deepest pool whose quote is allowlisted. Its decimals come from the allowlist entry for that address, never from the pool's symbol.

Live mode builds from the race response when it is younger than `QUOTE_TTL_MS`, its sell amount is unchanged, and its minimum output clears ours. The Jupiter quote goes straight to `/swap`, the Kyber route summary goes to the build call, and the 0x or LI.FI transaction is used as is. For 0x and Kyber the minimum output, recipient, and bought token are read from the calldata, not the API summary. Otherwise it re-quotes the chosen provider and refuses the send when the firm total impact is above the cap. Leg 2 of a two-hop is always quoted after leg 1 lands. Every firm call goes through the provider guard with `FIRM_TIMEOUT_MS`, and a 429 with `Retry-After` closes that provider until then. Solana simulates, then signs the Jupiter swap transaction. When `JITO_ENABLED=true`, the signed bytes go to Jito `sendTransaction` (plain send, not `bundleOnly`). EVM simulates with viem `simulateCalls` on the normal RPC, signs, and sends on `MEV_RPC_URL_<chainId>` when that variable is set. For Ethereum, set it to `https://rpc.flashbots.net`. The URL is not hardcoded. A hot-path ERC-20 approve is refused unless the allowance is already cached. One-time router approvals are a Turnkey root-quorum ceremony, then `APPROVAL_CACHE_JSON`. zkSync Era and Blast quote through LI.FI with `fromChain` equal to `toChain`. A LI.FI transaction whose chain id is anything else is rejected. zkSync live send stays off because those transactions are not standard EIP-1559.

Bridges are not on this path. `planRebalance` compares LI.FI, Across, Relay, and deBridge and returns `would_send` with `broadcast: false`. `execute` does not call it. The service does not submit a bridge transaction.

The signer is a `TransactionSigner`. Live mode uses Turnkey. The encrypted keystore is dry-run only. See [ADR 0001](adr/0001-turnkey-signer.md) and [ADR 0002](adr/0002-service-boundaries.md).

## One execute call for a second strategy

`POST /execute` takes a `SwapIntent` and always returns a dry-run, even when the process is live. Live broadcast is `POST /listing`. `execute()` in process still follows the mode it is given. The same caps and kill switch apply.

Hyperliquid is two surfaces. HyperEVM (chain id 999) is another EVM chain on 0x. HyperCore is the native book. When the spot pool is missing or under the liquidity floor and the ticker matches a non-delisted perp, the executor plans a 1x isolated update and an IOC order. The mark comes from `allMids`. There is no mark, so there is no order. The service signs only `order`, `cancel`, and `updateLeverage`.

## Where the numbers came from

Chain ids, RPCs, and aggregator coverage are the ones recorded on each chain in `src/chains.ts`, with the page that was checked. Robinhood Chain mainnet is chain id 4663 with the public RPC from Robinhood's connecting docs, and 0x lists it. HyperEVM mainnet is chain id 999. Monad mainnet is chain id 143 with `https://rpc.monad.xyz` from the Monad network page. 0x lists chain 143 on the Swap API, and KyberSwap lists the slug `monad`. DexScreener's slug was not on the pages checked, so Monad stays out of the default set until `ENABLED_CHAINS` includes it. Blast is quoted through LI.FI because 0x no longer lists it for swaps. No public RPC is invented for chains that did not publish one in those pages. Set `RPC_URL_<chainId>` or `SOLANA_RPC_URL`.
